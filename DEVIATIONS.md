## D22. Аудит обрывов и извлечения ответов Claude Code; догон рук (2026-09-14)

По запросу проведён аудит всех 208 ячеек рук Claude Code (`claude-plain`,

в `~/.claude/projects/<slug-work>/`; инструмент — `runners/audit_extraction.py`
(воспроизводимо, три класса дефектов).

### Что найдено

- **Дефект извлечения (класс D18), 1 ячейка.** `PVH-ARCH-001__claude-arch__dsf__r2`:
  агент записал полный документ (3 979 слов) в путь ячейки, раннер затёр его
  stdout-подтверждением («Записка готова…», 201 слово) → 6.25 балла, минимум руки.
- **Обрыв по лимиту вывода, 1 ячейка.** `CMP-ARCH-001__claude-plain__glm__r1`:
  документ сгенерирован двумя сообщениями (26 629 + 4 948 симв.), между ними пинг
  harness'а `Output token limit hit. Resume directly…`; сохранено только последнее
  → 10.25 балла при полном документе у судьи.
- **Ячейки без ответа, 46.** 4 × `claude-arch×dsp` — CLI падал с
  `[claude-code:unrecognized_model]` на неизвестном контекстном окне
  `deepseek-v4-pro` ДО обращения к API; 42 × glm — прогон был остановлен
  на 831/973 (D17).
- Остальные 160 ячеек — извлечение корректно: `answer.md` побайтово совпадает
  с итоговым сообщением сессии, все обязательные артефакты на месте, хвосты
  документов закрыты. Содержательные hard-fail (HF-01/02/03 на полных
  документах) не трогались — это валидные измерения.

### Ключевой факт: перегон НЕ лечит обрыв класса limit_split

Пользовательским решением обе повреждённые ячейки и 46 без ответа перегнаны
заново. Перегон `CMP-ARCH-001__claude-plain__glm__r1` **воспроизвёл дефект**
(новый журнал: 26 629 + 4 948 симв., тот же пинг). Причина — в режиме вывода,
а не в случайности: `claude -p --output-format text` печатает поле `result`,
равное тексту **последнего** сообщения хода; авто-продолжение после лимита —
это новый API-запрос и новое сообщение, поэтому начало документа в `result`
не попадает (подтверждено по документации CLI v2.1.270 и живьём).

**Детерминирован механизм, а не разбиение.** Две подряд генерации разбились
на чанки, третья (после перехода на stream-json) выдала весь документ одним
сообщением — 49 511 Б, D1–D10 полностью. То есть сама разбивка стохастична,
но если она произошла, text-режим гарантированно теряет начало. Поэтому класс
`limit_split` будет возникать и далее, и лечится он извлечением, а не повтором.

### Действие: полное извлечение вместо повторов

- `runners/run_matrix.py`: режим `PVBENCH_CLAUDE_STREAM=1` — рука claude
  запускается с `--output-format stream-json --verbose` (stream-json требует
  `--verbose`, иначе CLI выходит с ошибкой), ответ собирается
  `extract_claude_stream()`: склейка последнего сообщения с теми предыдущими,
  после которых был пинг лимита; блоки одного `message.id` объединяются,
  текст субагентов (`parent_tool_use_id`) отбрасывается, при нераспознанном
  потоке — фолбэк на сырой stdout.
- Режимы **эквивалентны** там, где потери не было (для сессии без сплита
  склейка даёт то же последнее сообщение), поэтому смешение режимов между
  ячейками сопоставимость не ломает; расходятся они ровно там, где старый
  результат был невалиден.
- Ячейки класса `limit_split` перегнаны точечно (`PVBENCH_CELLS="<glob>"`).
- Заодно в раннере: маскировка `ANTHROPIC_AUTH_TOKEN=***` в `cmd`
  (ключ ZHIPU_API_KEY попадал в `meta.json`/`generations.jsonl`) и env-фикс
  `CLAUDE_CODE_DISABLE_UNKNOWN_MODEL_WINDOW_ENFORCEMENT=1` для dsp.

### Бюджет времени: 1200 с в исходной руке против 3000 с в догоне

Исходная матрица считалась рабочим раннером с `TIMEOUT_AGENTIC = 1200`
(задача glm-ячейки Claude Code — медиана 1412 с), то есть потолок 20 минут
срабатывал у 56–83% glm-ячеек и отсекал самые долгие генерации. Экспортный
раннер, которым шёл догон, по умолчанию держит 3000 с; это зафиксировано
явно (`PVBENCH_TIMEOUT_AGENTIC=3000`).

По решению пользователя **вся glm-рука Claude Code (64 ячейки: claude-arch×glm
32 + claude-plain×glm 32) перегнана заново под единым бюджетом 3000 с и единым
извлечением (stream-json)** — чтобы сравнение arch против plain на glm было
сравнением одной популяции генераций, а не смесью «успевших за 20 минут» и
«успевших за 50». Прежние ответы 26 ячеек сохранены как `answer.preD22.md`
для сверки «старый бюджет против нового».

Итог для интерпретации: glm-рука Claude Code целиком получена под бюджетом
3000 с; остальные руки матрицы — под 1200 с. Сравнения Claude Code с другими
руками на glm следует читать с этой оговоркой (для dsf/dsp разница бюджетов
касалась 4–29% ячеек, для glm — всей руки).

### Инцидент 14.09: девятичасовой дедлок и что из него следует

Около 19:40 после сетевого транзиента **встали оба процесса**: генерация
PGL-ячеек и судья. Оба оказались в `futex_wait` — на внутренней блокировке,
а не на сети (сеть, машина и прокси проверены — исправны). Три сессии
провисли 9 ч 24 мин, судья столько же не выдавал вердиктов.

Причины и лечение:
- **раннер**: второй `communicate()` после `killpg` не был ограничен по
  времени. Если внуки CLI переживали `killpg` и держали пайпы, воркер висел
  вечно — тот же класс, что инцидент 11.09 (в комментарии кода), только
  прежнее лечение закрывало лишь первую половину. Теперь ожидание ограничено
  120 с, после чего пайпы закрываются;
- **судья**: обёрнут сторожем `judge_safe.sh` — порциями по 30 мин под
  внешним `timeout`, с повтором, пока неотсуждённых не останется.
  Идемпотентность (`judge.json` + `judge_1.json`) делает перезапуск
  безопасным;
- **наблюдение**: события-ориентированные сторожa не подают признаков жизни,
  когда процесс молча завис («тишина не есть успех»). Добавлен монитор
  сердцебиения: молчит при прогрессе, сигналит при 15 минутах простоя.

Данные при этом не потеряны — идемпотентность сохранена.
